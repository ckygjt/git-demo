## 0. 一句话定义

**给电商售后团队用的"证据核验助手"**：消费者提交售后申请后，Agent 综合**图片、诉求、聊天、订单、物流、账号历史、产品知识、跨工单记录**等多源信息，判断**这份证据能不能支撑这个诉求**，标出可疑之处与依据，并给出**分级的处置方式**——不是"通过 / 拒绝"二选一，而是让真实消费者顺利拿到补偿、让造假者在流程里自然暴露。同时把大量**可信**的投诉汇总起来，向品质、仓储、物流部门发出**质量预警**。

两句话概括价值：
1. **对每一单**：真的放心放行，存疑的换个更稳的处理方式，永不由 AI 拒绝。
2. **对全局**：不只防骗子，还帮品牌发现真问题。

## 1. 背景

### 1.1 业务现状【原话】
- 欧莱雅客服在工单中接收客诉：诉求 + **图片证据**，甚至附**医药费/医保证明**，申请退款、退货。
- 黄牛和恶意消费者用 AI **伪造包装破损、漏液图片**骗退款；AI 让伪造越来越容易。
- 欧莱雅也会收集抖音、小红书上的消费者内容，判断哪些需要跟进。
- 时效：天猫 30 秒、抖音 15 秒内响应，一对多接待；大促咨询量约为日常 15 倍。
- 服务原则："朋友心"——售后要**先相信消费者**；"求实心"——处理前看完整聊天、工单、订单、历史退款再判断。
- 欧莱雅已建**售后中台**，工单系统关联 14 个职能板块。

### 1.2 核心矛盾【推断】

```
   防骗退（品牌损失、运营压力）  ⇄  不误伤（消费者体验、舆情风险）
                         ＋
             没时间细看（时效紧、一对多）
```

客服今天只能二选一：**快速放行（被薅）** 或 **怀疑卡单（误伤、投诉、平台介入、舆情）**。

### 1.3 我们要解决的问题
让售后团队在**不增加处理时长**的前提下：可信的单放心处理，可疑的单**有据可依、有路可走**，并把可信投诉中隐藏的**质量问题**挖出来。

## 2. 用户与角色

| 角色 | 真实工作场景【行业】 | 核心诉求 | 优先级 |
| --- | --- | --- | --- |
| **售后审核专员** | 在售后工作台（如千牛、抖店后台 + 品牌售后中台）逐单处理退款/退货/补发申请 | 秒级知道这单怎么处理；可疑时知道疑点和依据、该换成哪种处理方式 | ★★★ **主用户** |
| **一线在线客服** | 在聊天工具（如千牛、飞鸽）接待咨询，消费者常在聊天中先发图诉苦 | 回复消费者时知道该怎么说、该让对方补什么 | ★★ |
| **二线复核 / 风控** | 处理升级的高风险单；平台介入时准备申诉材料 | 完整证据包；跨工单的团伙/惯犯线索 | ★★ |
| **品质 / 仓储 / 物流对接人** | 接收质量与破损问题反馈 | 及时知道哪个产品、批次、仓、线路出了问题 | ★★（质量预警接收方） |
| **客服主管** | 看团队与风险整体情况 | 风险分布、拦截情况、误判情况、预警 | ★ |
| **真实消费者** | 被服务对象，不直接使用系统 | **不被冤枉、不被反复刁难**，快速解决 | 约束条件 |
| **恶意申请者 / 黄牛** | 对抗方 | 以最低成本骗到退款 | 对抗对象 |

> **设计约束**：消费者永远看不到"风险分""疑似造假"等字样；系统对消费者只体现为合理的流程要求（如"请寄回商品，我们承担运费"）。【推断：朋友心原则】

## 3. 真实售后流程与痛点

### 3.1 电商售后的基本要素【行业】

| 要素 | 常见取值 |
| --- | --- |
| **售后类型** | 仅退款 / 退货退款 / 换货 / 补发 / 部分退款（小额补偿） |
| **售后原因**（下拉选择） | 包装破损、商品破损、漏液、少件/漏发、错发、质量问题、使用后过敏不适、与描述不符…… |
| **凭证** | 文字描述 + 若干图片（部分平台支持视频） |
| **关联信息** | 订单、物流轨迹、聊天记录、账号历史售后 |
| **升级路径** | 商家拒绝后消费者可申请**平台介入**；商家可向平台提交证据**申诉** |

> 关键洞察【推断】：**"仅退款"是骗退的主要入口**——不需要寄回商品，造假成本最低；而"退货退款"需要寄回实物，伪造的破损在验收时必然暴露。

### 3.2 当前流程

```
消费者提交售后申请（类型 + 原因 + 描述 + 图片）
        │                              ┌─ 消费者常先在聊天里发图、诉苦
        ▼                              │
售后工单进入工作台 ◀──────────────────┘
        │
        ▼
审核专员人工：看图 → 翻聊天 → 查订单/物流 → 查历史售后
        │
        ▼
凭经验决定 ──┬─▶ 同意（仅退款 / 补发）
             ├─▶ 要求补充凭证（话术因人而异）
             ├─▶ 升级主管
             └─▶ 拒绝 ──▶ 消费者申请平台介入 / 投诉 / 社媒曝光
```

### 3.3 痛点

| # | 痛点 | 后果 | 来源 |
| --- | --- | --- | --- |
| P1 | AI 伪造的破损/漏液图肉眼难辨 | 被骗退款 | 【原话】 |
| P2 | 时效紧，信息散在多个系统（工单、聊天、订单、物流），没时间全看 | 凭感觉处理 | 【原话】+【推断】 |
| P3 | 分不清"无害编辑"与"欺诈篡改" | 好人被怀疑 | 【原话】修脸例子 |
| P4 | 只看单张图，看不到跨工单信号 | 惯犯、团伙难识别 | 【原话】交叉识别 |
| P5 | 处置只有"同意 / 拒绝"两个极端 | 拒绝引发冲突，同意被薅 | 【推断】 |
| P6 | 疑点说不清 | 二线要重看；平台介入时拿不出证据 | 【推断】 |
| P7 | 大量真实的破损投诉只被逐单处理，没人汇总 | 包装缺陷、仓库/快递问题长期存在，持续产生售后成本 | 【推断】 |

## 4. 用户需求（JTBD）

**售后审核专员（主用户）**
- **J1**：打开工单时，我想一眼看到**建议的处理方式**和**可信程度**，可信的单秒处理。
- **J2**：有疑点时，我想看到**疑点在哪里、来自哪类信息、为什么可疑**，能自己确认而不是盲信。
- **J3**：拿不准时，我想要一个**不和消费者起冲突又能防住风险**的处理方式和现成话术。
- **J4**：图上有与诉求无关的编辑（美颜等）时，系统不要误报。

**一线在线客服**
- **J5**：消费者在聊天里发图时，我想知道该怎么回复、要不要请对方补拍什么。

**二线复核 / 风控**
- **J6**：高风险单升级给我时，我想拿到**完整证据包**，也能直接用于**平台申诉**。
- **J7**：我想看到跨工单关联（同图、相似文案、同账号多次申请）。

**品质 / 仓储 / 物流**
- **J8**：当某个产品、批次、仓或快递线路的**可信**破损/漏液投诉异常增多时，我想**第一时间收到预警**和代表性证据。

## 5. 多源证据体系（核心）

> 原则：**图片只是证据之一**。每类信息都要做到：提取什么 → 核验什么 → 哪些信号**增加**可信度、哪些**降低**可信度 → 演示时数据从哪来。
> 可信度判断是**双向**的：既找疑点，也找能证明消费者说的是真话的证据。

### 总览

| # | 信息源 | 核心作用 | 信号强度 | 演示数据 |
| --- | --- | --- | --- | --- |
| S1 | 凭证图片（像素） | 是否伪造/篡改；篡改是否落在诉求部位 | 强 | 自拍 + 自生成 + 公开数据集 |
| S2 | 凭证图片（内容） | 图里是什么产品、什么规格、哪里坏了、批号 | 强 | 同上 |
| S3 | 图片元数据 | 拍摄时间、设备、是否截图/转发 | 弱 | 构造 |
| S4 | 诉求文本 | 问题类型、部位、诉求；与图是否一致 | 中 | 构造 |
| S5 | 聊天记录 | 前后说法是否一致；话术模板化 | 中 | 构造 |
| S6 | 订单 | SKU、规格、件数、赠品；与图是否一致 | 强 | 构造 |
| S7 | 物流 | 签收时间、轨迹异常、线路破损率 | 中 | 构造 |
| S8 | 账号历史 | 退款频率与类型、账号资历 | 弱（仅辅助） | 构造 |
| S9 | 跨工单记录 | 同图/近似图/同文案在其他工单出现 | 强 | 构造 |
| S10 | 产品知识库 | 该 SKU 真实包装是什么样、可能怎么坏 | 强 | 公开产品信息整理 |
| S11 | 批次与群体投诉 | 同批次/同仓/同线路是否集中出现可信投诉 | 中（增信为主） | 构造 |
| S12 | 流程中新证据 | 补拍凭证、退货验收结果 | 强（验收为最终真值） | 构造 |

### S1 凭证图片 · 像素层取证
- **提取**：AI 生成概率、篡改区域热力图、压缩/噪声一致性。
- **核验**：
  - 整图是否为 AI 生成；
  - 局部是否被重绘/拼接，**可疑区域位置**；
  - 物理合理性：高光、反光方向、液体形态、阴影、材质纹理（主理人点名的线索）【原话】。
- **降信**：可疑区域**与诉求部位重叠**（如漏液处被重绘）。
- **不计风险**：可疑区域落在人脸、背景、无关物体（美颜、换背景）【原话】。
- **注意**：截图、多次压缩会让检测器不稳 → 单靠 S1 不能定高风险，需其他信息印证（见第 7 章融合规则）。

### S2 凭证图片 · 内容理解
- **提取**：品牌、品名、规格（如 30ml/50ml）、包装形态（瓶/管/罐/盒）、**破损位置与形态**（泵头断裂、瓶身裂纹、外盒压痕、漏液位置）、**瓶身批号**（OCR）、是否与快递面单同框。
- **核验**：与 S4 诉求、S6 订单、S10 产品知识对齐。
- **增信**：商品、规格、批号与订单一致；破损形态符合物理常识；与快递外箱/面单同框。
- **降信**：图中产品与订单不符；看不到诉求所说的问题；批号与发货批次不符【假设：品牌仓库记录发货批次】。

### S3 图片元数据
- **提取**：EXIF 拍摄时间、设备型号、编辑软件标记；是否截图（分辨率、状态栏特征）。
- **核验**：拍摄时间是否早于签收时间（"收货前就拍了破损照"）。
- **重要限制**【行业】：平台上传常会**剥离 EXIF**，**缺失元数据不能视为可疑**，只在"有且矛盾"时作为弱证据。

### S4 诉求文本
- **提取**：售后类型、原因、问题部位、问题程度、诉求金额、时间描述（如"刚收到就……"）。
- **核验**：诉求与图片内容（S2）一致；诉求类型与产品结构（S10）在物理上是否可能。
- **降信**：说漏液但图中无液体痕迹；说瓶身碎裂但图中为外盒压痕；描述与模板文案高度相似（见 S9）。
- **增信**：描述具体、细节与图片吻合（如说"泵头歪了按不出来"，图中可见泵头倾斜）。

### S5 聊天记录
- **提取**：消费者首次反馈的问题与时间、情绪、是否先咨询过使用方法等。
- **核验**：聊天中说法与售后申请是否一致（先说"不喜欢味道"、后申请"漏液"）【原话：上下文冲突】。
- **增信**：首次反馈及时、前后一致。
- **降信**：说法变化且向更易获赔的原因靠拢。

### S6 订单
- **提取**：SKU、规格、数量、赠品、套装构成、支付金额、下单时间。
- **核验**：图中商品是否属于本订单（含赠品、套装组件）；申请件数是否超出购买件数；金额是否合理。
- **降信**：图中商品不在订单内；申请数量 > 购买数量。

### S7 物流
- **提取**：发货仓、快递公司、线路、签收时间、轨迹异常节点（如"外包装破损""拒收""滞留"）。
- **核验**：申请时间距签收时间（"收到即破损"却签收 N 天后才申请）；轨迹中是否已有破损记录。
- **增信**：**轨迹中有破损/异常记录**；该线路近期破损投诉偏高（见 S11）。
- **降信**：长时间后才报"到货破损"，且无其他增信信号。

### S8 账号历史
- **提取**：近 N 天售后次数与类型、仅退款占比、账号注册时长、累计消费、会员等级。
- **核验**：是否短期内多次以同类原因申请仅退款。
- **定位**：**只作辅助信号，单独不能升级风险**——高频购买者的售后次数天然更多；老会员、高消费可作为增信。【推断：避免误伤】

### S9 跨工单记录
- **提取**：图片感知哈希/特征向量、诉求文本向量、收货信息（演示用）。
- **核验**：同图或近似图出现在其他订单/账号；不同账号使用高度相似的诉求文案【原话：交叉素材、账号特征】。
- **降信**：**同一张图用于多个工单**（强证据，可直接展示关联工单作为依据）。

### S10 产品知识库（"懂美妆"的关键）
- **内容**：每个 SKU 的容器类型（玻璃瓶/塑料瓶/软管/铝管/罐）、开口结构（泵头/滴管/旋盖/喷头）、规格、外盒形态、瓶身印刷要素（品名、规格、批号位置）、**易损部位与常见真实破损形态**、液体性状（颜色、黏稠度）。
- **核验**：
  - 诉求在物理上是否可能（软管不会"碎裂"，但可能封口爆裂）；
  - 图中包装细节是否符合正品（文字、Logo、规格印刷）；
  - 液体颜色/质地是否符合该产品（精华液、乳液、粉底液差异明显）。
- **增信**：破损形态与该包装的常见真实破损一致。
- **降信**：不可能的破损方式；包装细节与正品不符（AI 生成常见文字畸变）。

### S11 批次与群体投诉
- **提取**：按 SKU / 批次 / 发货仓 / 快递线路 / 时间窗口聚合的投诉量与可信度分布。
- **作用**：
  - **对单个工单增信**：同批次、同线路近期有多起**可信**同类投诉 → 这单更可能是真问题；
  - **对全局**：触发质量预警（见第 9 章）。

### S12 流程中产生的新证据
- **补拍凭证**：按疑点提出的具体补拍要求（如"拍瓶底批号""外箱面单与商品同框"）。
- **退货验收结果**：仓库收货检查结论，是**最终真值**，回流用于：① 校准判断规则与阈值；② 评估误报/漏报；③ 补充 S9 的跨工单库。

## 6. 风险类型地图

> 每种风险标注主要依赖的信息源。

### 6.1 证据造假类
| 类型 | 表现 | 主要信息源 |
| --- | --- | --- |
| R1 AI 生成破损/漏液 | 整图或局部生成 | S1、S2、S10 |
| R2 局部篡改 | 真实图上 P 出裂痕/漏液 | S1、S2 |
| R3 挪用 | 网图、他人晒单、别家产品图 | S2、S6、S9 |
| R4 重复使用 | 同图多单 | S9 |
| R5 皮肤问题图造假 | 过敏/烂脸图为网图或生成 | S1、S9（特殊处理见 7.4） |
| R6 单据伪造 | 诊断书、医药费单据被 P | S1、S2（Should） |

### 6.2 内容冲突类
| 类型 | 表现 | 主要信息源 |
| --- | --- | --- |
| C1 图与订单不符 | 产品/规格/批号不对 | S2、S6 |
| C2 图与诉求不符 | 说漏液看不到漏液 | S2、S4 |
| C3 诉求与产品不符 | 物理上不可能的损坏 | S4、S10 |
| C4 时间线矛盾 | 拍摄早于签收、签收很久才报到货破损 | S3、S7 |
| C5 前后说法矛盾 | 聊天与申请原因不一致 | S4、S5 |

### 6.3 行为类（辅助）
| 类型 | 表现 | 主要信息源 |
| --- | --- | --- |
| B1 高频仅退款 | 短期多次同类申请 | S8 |
| B2 模板化文案 | 多账号诉求雷同 | S9 |

### 6.4 必须放行的情况（防误伤）
| 类型 | 例子 |
| --- | --- |
| N1 与诉求无关的编辑 | 美颜、修脸、换背景，但破损部位真实【原话】 |
| N2 正常处理 | 裁剪、旋转、加箭头圈注、压缩、截图转发 |
| N3 拍摄质量差 | 模糊、暗光、反光 → 请补拍，而非判风险 |
| N4 元数据缺失 | 平台剥离 EXIF |

## 7. 判定逻辑

### 7.1 第一原则：痕迹 × 相关性【原话推出】
**一个可疑点算不算风险，取决于它是否与诉求相关。** 篡改落在诉求主张的部位才计入；无关编辑只做备注。

### 7.2 证据融合规则【假设，待数据集验证】
1. **单一弱信号不升级**：仅 S3/S8 等弱信号，不能把工单判为中/高风险。
2. **高风险需至少一条强证据**：如 S1 可疑区域与诉求重叠、S9 同图多单、C1/C3 明确冲突。
3. **增信可以抵消**：如 S7 轨迹显示外包装破损、S11 同批次可信投诉集中，可下调风险。
4. **证据不足不硬判**：信息缺失或图片质量差 → 结论为"需补充凭证"，而不是"可疑"。
5. **每条结论必须可追溯**：风险点 = 信息源 + 位置/字段 + 说明 + 置信度。

### 7.3 三级结论
| 等级 | 含义 |
| --- | --- |
| **可信** | 无与诉求相关的疑点，或增信信号充分 |
| **存疑** | 有疑点但不足以下结论，或信息不足 |
| **高风险** | 至少一条强证据 + 其他信号印证 |

### 7.4 健康安全类诉求的特殊处理【推断】
"使用后过敏、不适"类诉求涉及消费者健康：
- **不走"防骗"逻辑**，优先安抚并转专人（消费者关怀/专业团队）跟进；
- 系统只做**凭证整理**（如单据关键字段是否完整），疑点仅作为专人参考，不作为处置依据。

## 8. 处置分级（核心差异点 ①）

> 思路：**不判"真假"，而是根据可信度选择"合适的处理方式"**。真实消费者照样得到补偿，造假者在流程中自然暴露。AI 不做拒绝决定。

### 8.1 可信度 → 处置方式

| 结论 | 建议处置 | 对真实消费者 | 对造假者 |
| --- | --- | --- | --- |
| **可信** | 按诉求直接处理：仅退款 / 补发 / 小额补偿 | 秒过，无感 | — |
| **存疑（信息不足）** | **定向补充凭证**：按疑点生成具体补拍要求 | 多一步，要求合理 | 难以按指定角度补出一致的伪造图 |
| **存疑（有疑点）** | **改为退货退款，商家承担运费 / 上门取件** | 照样拿到退款，只是需寄回 | 伪造的破损在验收时暴露 |
| **高风险** | 退货退款 + **仓库重点验收** + 二线复核；生成**证据包**备平台介入 | 真问题仍可正常获赔 | 无法通过实物验收；平台介入时商家有据可依 |

### 8.2 定向补拍要求示例【行业 + 推断】
| 疑点 | 补拍要求 |
| --- | --- |
| 看不清破损位置 | 请从侧面近距离拍摄破损处 |
| 图中商品无法确认属于本订单 | 请拍摄瓶底批号 / 外箱快递面单与商品同框 |
| 漏液痕迹可疑 | 请拍摄商品与外箱内部的液体痕迹 |
| 规格与订单不符 | 请拍摄瓶身规格标识 |

### 8.3 话术示例（系统生成，客服可编辑）【假设】
- 存疑 → 改退货退款：
  > "亲，非常抱歉让您遇到这个问题～为了尽快帮您处理，这边为您安排上门取件，运费由我们承担，商品寄回后马上为您办理退款哦。"
- 存疑 → 补拍：
  > "亲，为了帮您更快处理，麻烦您从侧面再拍一张破损位置的照片，并让外箱快递面单一起入镜，这边收到后立即为您跟进～"

> 话术遵循"朋友心"：先致歉安抚，再提要求，**不出现任何怀疑性字眼**。

### 8.4 闭环
```
处置建议 → 客服采纳/修改 → 执行 → 退货验收结果 / 补拍结果
                                        │
                                        ▼
                      回流：校准阈值、统计误报漏报、补充跨工单库
```

## 9. 质量预警（核心差异点 ②）

> 思路：被判为**可信**的投诉不是处理完就结束，而是**有价值的质量信号**。系统从"防骗工具"升级为"品牌的质量雷达"。【推断：呼应直播"从单个 case 到全链路优化"】

### 9.1 聚合维度
SKU × 批次 × 发货仓 × 快递公司/线路 × 时间窗口

### 9.2 预警触发【假设】
某维度组合下，**可信**的同类投诉（如漏液、泵头损坏）数量显著高于历史基线。只统计可信投诉，避免被造假投诉污染。

### 9.3 预警内容与流向

| 预警类型 | 示例 | 推送给 |
| --- | --- | --- |
| 包装/产品质量 | "某精华 X 批次近 7 天泵头断裂投诉显著上升" | 品质部门 |
| 仓储打包 | "X 仓发出的玻璃瓶产品破损率高于其他仓" | 仓储 |
| 物流运输 | "X 快递发往某区域的外盒压损投诉集中" | 物流对接 |

每条预警附：投诉数量与趋势、**代表性可信证据图**、涉及订单、建议动作（如抽检该批次、加强该品类打包、与快递沟通）。

### 9.4 对单个工单的反哺
同批次/线路存在已确认的质量问题时，后续同类投诉自动**增信**（S11），处理更快，减少对真实受害消费者的打扰。

## 11. 目标效果

### 11.1 演示用例

| 用例 | 关键信息 | 系统表现 |
| --- | --- | --- |
| U1 真实破损 + 美颜自拍 | S1 人脸区域有编辑，破损区真实 | **可信**，直接处理；备注"人像有美颜，与诉求无关" |
| U2 AI 生成漏液图 | S1 漏液区可疑 + S10 液体颜色不符该产品 | **存疑/高风险** → 改退货退款 + 上门取件；V2 标出漏液区与依据 |
| U3 同图多单 | S9 命中 3 天前另一账号工单 | **高风险** → 退货退款 + 重点验收；证据包展示关联工单 |
| U4 产品不符 | S2 识别为 30ml，S6 订单为 50ml | **存疑** → 请补拍瓶身规格 |
| U5 物理上不可能 | 诉求"瓶身碎裂"，S10 该 SKU 为软管 | **存疑** → 请补拍破损处 |
| U6 轨迹有破损记录 | S7 物流节点"外包装破损"，图片轻微可疑 | **可信**（增信抵消），直接处理 |
| U7 照片模糊 | 无法判断 | **存疑（信息不足）** → 请补拍清晰照片，不判风险 |
| U8 过敏投诉 | 健康类 | 不走防骗逻辑，转专人；只整理凭证 |
| U9 批次预警 | 同批次多起可信漏液投诉 | V3 生成质量预警推送品质部门 |

### 11.2 量化目标【假设：在自建数据集上验证】

| 指标 | 含义 | 目标 |
| --- | --- | --- |
| **误报率** | 真实证据被判"存疑/高风险"的比例 | **≤ 10%（最优先）** |
| 拦截率 | 造假证据被判"存疑/高风险"的比例 | ≥ 80% |
| 依据覆盖率 | 存疑/高风险结论附可追溯依据的比例 | 100% |
| 单工单核验时长 | 从提交到出结果 | ≤ 30 秒（工单入队时异步完成） |
| 单工单成本 | 模型调用费用 | 展示并尽量降低 |

**为什么误报优先**：冤枉一个真实消费者可能引发投诉与舆情；而漏掉的造假还有"补拍 → 退货验收 → 二线复核"多道防线。并且由于存疑单的处置是"改为退货退款"而非拒绝，即便误报，对真实消费者的伤害也被降到最低。

## 13. Agent 执行流程【推断：对齐赛题"构建 Agent"与评委对 Agent 的定义】

```
1. 读取工单 → 理解诉求（类型、部位、诉求、时间描述）
   └─ 若为健康安全类 → 走特殊流程（7.4）
2. 规划核验步骤：按诉求决定查什么
   （漏液 → 液体区域取证 + 液体性状比对；错发 → SKU/规格比对；到货破损 → 物流轨迹）
3. 调用工具（并行）：
   ├─ 像素层取证（S1）
   ├─ 图像内容理解 + 批号 OCR（S2）
   ├─ 元数据解析（S3）
   ├─ 订单 / 物流 / 聊天 / 账号历史查询（S5–S8）
   ├─ 跨工单检索（S9）
   ├─ 产品知识库查询（S10）
   └─ 批次群体投诉查询（S11）
4. 交叉验证：可疑区域 × 诉求部位；图 × 订单 × 产品知识；时间线；增信/降信汇总
5. 证据不足 → 生成定向补拍要求，而不是硬下结论
6. 输出：结论 + 逐条依据 + 处置建议 + 话术 + 证据包
7. 写回：结果进入跨工单库与批次聚合（S9、S11）
```
